## 改进计划

### 问题 1：`IWavelength` 的 `Value` 属性不存在（核心阻塞问题）

**根因分析：**

当前代码使用 `gencache.EnsureModule()` + `EnsureDispatch()` 进行**早期绑定**（early binding）。这会让 win32com 生成 Python 包装类到 `gen_py` 缓存目录。但 2018 版 ZOS-API 的 `IWavelength` 接口的属性名，在生成的包装类中可能与直接的 `.Value` 不匹配。

具体来说，`sys_data.Wavelengths.GetWavelength(i)` 返回的 COM 对象，其 Python 生成代码可能把属性暴露为 `_prop_map_get_` 字典中的键，但不一定作为 Python 属性直接可达。在 tools.py 中 `w.Value` 直接访问就会失败。

**PyZOS 的做法：**
PyZOS 在 [zosutils.py](https://raw.githubusercontent.com/xzos/pyzos/master/pyzos/zosutils.py) 中通过 `_prop_map_get_` / `_prop_map_put_` 字典来动态发现 COM 对象的实际可用属性，并用 `CastTo()` 进行类型转换。它从不直接 `.Value`，而是通过 `ZOSPropMapper` 描述符和 `wrapped_zos_object()` 层包装所有属性访问。

**修复方案（3 层策略）：**

1. **清理 gen_py 缓存** — 在 zemax_connection.py 的 `connect()` 方法调用 `EnsureModule` 前，先删除旧缓存重新生成。
2. **安全属性访问辅助函数** — 改写 `_safe()` 为多策略探测函数：
   ```
   尝试顺序：
   a) 直接属性访问: getattr(obj, attr)
   b) CastTo 目标接口后访问: CastTo(obj, 'IWavelength').Value
   c) 从 _prop_map_get_ 字典读取属性
   d) 用 Invoke 方法调用 COM 底层
   ```
3. **COM 对象诊断工具** — 新增一个调试方法，在启动时检测 `IWavelength`、`IField` 等关键对象的实际属性布局，一次性确定正确的访问路径并缓存，后续直接使用。

**涉及文件：**
- zemax_connection.py — 添加缓存清理逻辑  
- tools.py — 重写 `_safe()` 函数 + 重写 `get_system_info()` / `set_wavelengths()` 中的波长和视场访问逻辑

### 问题 2：CLI 运行中断开后无法重连

**根因分析：**

当前 zemax_connection.py 只在启动时 `connect()` 一次。在 Zemax 侧断开 Interactive Extension 后，COM 对象引用失效，但 Python 侧没有检测连接状态的机制，所有后续工具调用都会抛出 COM 异常。

**PyZOS 的做法：**
PyZOS 的 `_PyZOSApp` 使用 `connect.IsAlive` 属性检测连接状态，并在 `OpticalSystem` 类中暴露为 `pConnectIsAlive` 属性。

**修复方案：**

1. **`ZemaxConnection` 中新增 `is_alive` 属性** — 通过 `self._connection.IsAlive` 检测连接是否存活。
2. **`ZemaxConnection` 中新增 `reconnect()` 方法** — 保存连接参数 (`mode`, `instance`)，断开旧引用后重新执行 `connect()` 流程。
3. **`ZemaxToolkit.dispatch()` 中添加自动重连** — 在每次工具调用前检测 `is_alive`，若断开则提示用户在 Zemax 中重新打开 Interactive Extension，然后自动尝试重连，有 3 次重试机会。
4. **CLI 增加 `reconnect` 命令** — 用户输入 `reconnect` 可手动触发重连。

**涉及文件：**
- zemax_connection.py — `is_alive`, `reconnect()`
- tools.py — `dispatch()` 增加前置连接检查
- main.py — CLI 增加 `reconnect` 特殊命令

### 问题 3：无法操作已有系统

**根因分析：**

这个问题实际上是问题 1 的连锁反应。`get_system_info()` 因为 `IWavelength.Value` 报错，LLM 看到错误后认为系统异常，于是调用 `new_file()` 创建新空系统，把用户已有的设计覆盖了。

修复问题 1 后，`get_system_info()` 能正确读取已有系统数据，LLM 自然不会再错误地创建新系统。

**额外改进：**
- 在 `new_file` 工具的 system prompt 中强调：**除非用户明确要求，否则不要调用 new_file**。
- 给 `new_file` 工具增加确认机制，在执行前先让 LLM 回复确认。

**涉及文件：**
- main.py — 修改 SYSTEM_PROMPT
